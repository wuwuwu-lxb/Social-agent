# 阶段总结：微信联调通过，下一步进入真实发布

日期：2026-11-13。

## 当前结论

用户在本次会话确认微信端验证没有问题。该记录属于本人实测反馈，
没有附带聊天截图或模型调用轨迹，不编造额外的测试次数、耗时或成功率。
当前链路已支持从微信触发 AstrBot 插件，创建微博文本草稿并进行真实网页预演。
插件没有实际提交入口，真实发帖、评论、点赞仍未完成验收。

## 从建仓到当前的路线

1. 创建 Social-agent 仓库，划分代码、技术文档和本地 PPT 目录。
2. 选择 AstrBot 为对话与模型底座，以微信为用户入口、微博为目标平台。
3. 探索官方 CLI 0.9.8，完成安装、Windows 授权问题定位与修复、授权及目录查询。
4. 导出 75 项官方接口定义，保留名称、参数和能力对照。用户考虑额度限制，
   决定探索浏览器执行方案，不以目录数量代表业务实现数量。
5. 建立 webmcp 和自建 Playwright 两个实验分支，分别验证现成适配器与 DOM 路线。
6. 发现上游登录误判、捕获启动过晚和 DOM 选择器变化等问题。
   增加独立登录检查，在导航前启动捕获后，真实动态、详情、评论读取与发帖预演通过。
7. 编写临时 `/weibo_probe bridge` 诊断命令，用真实 AstrBot SDK 验证插件至浏览器的调用。
8. 提取独立正式插件 v0.1.0，注册 `weibo_statuses_update` 草稿预演工具，
   保存 SQLite 任务，提供创建及查询命令。
9. 真实插件管理器测试与本机后端加载通过，用户进一步确认微信端验证通过。

实验提交与复现方法见 `browser-experiments.md`、`weibo-probe.md`。
正式插件基线提交为 `ca85fc6`，位于 `codex/plugin-weibo`。

## 完整链路及执行边界

微信消息由已有平台适配器进入 AstrBot。模型理解请求并选择工具，
把文案转换为 `weibo_statuses_update(status)` 的结构化调用。
Python 插件检查私聊权限和参数，通过固定 Node 入口传递 JSON。
Node 执行器调用 webmcp 微博适配器，由 Playwright 控制专用 Edge 会话，
在真实微博网页定位输入框并填写文案。结果回传插件、保存任务，再经 AstrBot 回复微信。

当前使用适配器模块 API，没有通过 MCP 服务连接。
模型负责理解和选择工具，适配器负责固定网页操作，不在每次请求时生成任意浏览器代码。
当前最后一步是预演，尚未点击发送。未来实际提交及平台结果读回需要独立实现。

## 下一步实际工作

首要目标是真实文本发布：确定测试文案和操作人，展示最终内容并确认，
实现提交、内容声明、平台 ID/链接提取和正文读回。成功必须有平台证据。
提交后超时应记录结果未知，先核对再决定重试，避免重复发布。

随后按读取、发帖、评论、指定评论回复、点赞顺序完善工具链。
现成适配器缺少点赞工具，各操作的参数和结果需逐项验收。
将实验分支已验证的读取能力迁入正式插件，不能把实验成功直接算作正式模型工具可用。

工具链稳定后，开展角色智能体行为模拟。先固定模型、输入主题和可互动对象，
设置角色目标、表达风格、历史记忆与行动范围，记录其发帖、回复或不行动的选择。
离线重放相同场景，对照基础提示词与角色配置的内容一致性、行动合理性，
再在受控真实账号上验证执行。当前尚未开展角色实验，也没有量化结果。
